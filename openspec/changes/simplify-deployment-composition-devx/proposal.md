## Why

当前部署/本地开发入口混合了“核心服务”和“可选依赖服务”的边界，导致用户难以判断最小可运行拓扑，也难以按自身基础设施复用已有服务。现在需要明确 Crystalith 的核心形态：前端 + 后端为必需，其余能力通过可选子服务组合接入。

## What Changes

- 引入统一的“服务组合（composition）”模型，固定核心服务为 `frontend` 与 `backend`。
- 采用 Docker Compose 原生组合能力作为唯一主路径：`-f` 合并 + `profiles`，保持用户命令直觉一致、无额外工具惊讶。
- 将向量库、Embedding/LLM 网关、缓存、离线模型服务等标记为可选子服务，支持启用/禁用与外部地址接入。
- 明确规范名与实现名映射：规范中的 `frontend/backend` 分别映射到 Compose 服务名 `web/api`。
- 统一 `deployments/` 目录分层规则（核心基线、可选增强、环境覆盖），并通过共享片段减少重复配置。
- 统一本地开发与部署入口语义，提供一致的 overlay/profile 组合机制与默认降级行为。
- 增加可观测的依赖探活状态，区分“核心可用”与“可选增强可用”。
- 更新配置与文档，明确最小启动路径、可选增强路径、以及用户自托管路径。

## Capabilities

### New Capabilities
- `service-composition-profiles`: 定义核心服务与可选子服务的组合机制、契约与降级行为。

### Modified Capabilities
- `delivery-and-deployment`: 将部署入口从“固定绑定服务集”调整为“核心 + profile 可选组合”模型。
- `config-and-models`: 增强配置覆盖规则，支持可选服务独立启用策略与外部服务接入策略。

## Impact

- 后端：配置加载与依赖探活流程、可选能力降级路径、健康状态暴露。
- 前端：开发启动说明与错误提示语义（区分核心故障和可选服务故障）。
- 部署：`deployments/` 与本地开发启动脚本/文档重构，减少强绑定默认依赖。
- 测试：新增组合矩阵（核心-only、核心+可选、本地可选服务缺失但核心可用）。
- 维护：不引入强模板化/自定义 DSL 作为主路径，降低长期认知负担。
