## Context

- 面向公共用户后，仓库需要提供“可发现、可贡献、可求助、可安全披露”的最小闭环，否则用户会在 README/Docs 之外缺少下一步。
- 当前仓库已具备一定文档与 CI 基础，但仍缺少标准治理文件（如 `SECURITY.md`、Issue/PR 模板），并存在部分占位元数据（例如后端包描述）。

## Goals / Non-Goals

**Goals:**

- 提供公共仓库的最小治理与支持入口：
  - 安全漏洞报告路径（`SECURITY.md`）
  - 贡献指南（`CONTRIBUTING.md`，可复用 docs 内容并做索引）
  - Issue/PR 模板（降低信息来回成本，提升可维护性）
- 修正明显占位/不一致元数据，使 README/Docs/包元数据对“Crystalith 是什么”给出一致表述。
- 保持改动轻量、低维护：不引入复杂的流程或需要长期运维的机器人体系作为前置条件。

**Non-Goals:**

- 不改变核心产品功能与 API 语义（仅工程化与文档/治理层调整）。
- 不一次性建设完整社区治理体系（如复杂的 triage 流程、路线图工具等）。

## Decisions

1. **治理文件采取“最小可用集合”**
   - 必选：`SECURITY.md`、`CONTRIBUTING.md`、Issue 模板（bug/feature）。
   - 可选：`CODE_OF_CONDUCT.md`、`CHANGELOG.md`（可在发布流程稳定后再加）。

2. **贡献文档以“入口索引 + 指向现有文档”为主**
   - `CONTRIBUTING.md` 不重复长篇说明，而是提供：
     - 本地开发/测试命令最小清单
     - 代码结构指引
     - OpenAPI/生成客户端的同步方式
     - 提交信息规范与 PR 预期内容
   - 详细说明仍以 `docs/` 为主（降低多处维护风险）。

3. **Issue/PR 模板强调可复现与验收信息**
   - Bug 模板要求：复现步骤、期望/实际、环境（local/compose）、日志/截图（如适用）。
   - Feature 模板要求：动机、用户故事、验收标准、是否涉及 breaking change。

4. **元数据一致性以“用户第一眼”视角校验**
   - 修正后端包描述等占位字段，使其与 README/Docs 的产品定位一致。

## Risks / Trade-offs

- **[风险] 安全披露渠道不明确或不可达** → **缓解**：`SECURITY.md` 提供明确联系方式与响应范围，并避免暴露敏感信息。
- **[风险] 模板过度严格导致用户不愿提 issue** → **缓解**：模板保持简短，并允许“未知/暂缺”字段，优先降低来回沟通成本。
