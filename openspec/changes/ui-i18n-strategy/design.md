## Context

- 前端 Workspace 现有大量用户可见文案为中文（按钮、提示、空态、错误信息），而文档与对外入口多为英文；这会导致：
  - 面向不同语言用户时缺少一致体验；
  - 文案分散在组件中，难以统一修改与审校；
  - 未来要做双语/多语会变成“全量重构”，风险更大。

## Goals / Non-Goals

**Goals:**

- 定义清晰的语言策略（默认语言、覆盖范围、切换/持久化规则）。
- 建立最小 i18n 基础设施（不要求一开始就翻译全站），允许增量迁移现有硬编码字符串。
- 先覆盖 Workspace 关键路径（Sources/Chat/Studio/诊断/导出/空态），确保“核心路径可全程同一语言”。

**Non-Goals:**

- 不在本变更内完成所有页面/所有文案的全量翻译（允许分阶段）。
- 不引入复杂的翻译平台/外部 SaaS 作为硬依赖（可在后续引入）。
- 不改变后端 API 文案/错误码体系（仅 UI/Docs 文案治理与可选多语言）。

## Decisions

1. **语言集合与默认策略**
   - 支持至少两种 locale：`zh-CN` 与 `en`。
   - 默认 locale：
     - 优先跟随浏览器语言（若匹配 `en`/`zh-CN`）；
     - 否则回退到 `en`（更适合公共仓库的默认面向）。
   - 用户手动选择后写入 `localStorage`，覆盖自动检测。

2. **最小 i18n 实现：轻量字典 + hook**
   - 在 `frontend/web/src` 增加一个集中式消息字典（按域分组：workspace/sources/chat/studio/common）。
   - 提供 `t(key, params?)` 与 `useLocale()`/`useI18n()` hook，避免在组件内散落字符串。
   - Key 采用稳定、可搜索的命名（例如 `workspace.onboarding.no_sources.title`），并在 TypeScript 层做基本类型约束（防止 key 漏拼）。

3. **增量迁移策略**
   - Phase 1：仅迁移 Workspace 核心路径的“高频与阻塞”文案（空态/错误/导出/上传提示）。
   - Phase 2：迁移剩余面板与边缘弹层文案，并补齐英文翻译。
   - 迁移期间允许少量遗留硬编码，但必须逐步减少，避免新增硬编码字符串。

4. **入口与可发现性**
   - 在 Workspace Header（或设置菜单）提供语言切换入口；切换后即时生效且不刷新页面也可工作。

## Risks / Trade-offs

- **[风险] 翻译质量与术语一致性** → **缓解**：建立简短术语表（Sources/Session/Notebook 等）并在字典中复用；先覆盖核心路径再扩展。
- **[风险] 迁移过程中出现中英文混杂** → **缓解**：以“关键路径全覆盖”为第一里程碑；禁止在关键路径继续新增硬编码中文字符串。
- **[风险] 引入 i18n 依赖导致体积/复杂度上升** → **缓解**：先用轻量字典实现；若未来需要复数规则/日期本地化再引入成熟库。
