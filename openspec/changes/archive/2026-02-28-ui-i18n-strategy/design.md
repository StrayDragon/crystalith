## Context

- 前端 Workspace 现有大量用户可见文案为中文（按钮、提示、空态、错误信息），而文档与对外入口多为英文；这会导致：
  - 面向不同语言用户时缺少一致体验；
  - 文案分散在组件中，难以统一修改与审校；
  - 未来要做双语/多语会变成“全量重构”，风险更大。

## Goals / Non-Goals

**Goals:**

- 定义清晰的语言策略：**UI 仅内置 `zh-CN`**，覆盖 Workspace 关键路径并消除阻塞性的中英文混杂。
- 建立最小 i18n 占位基础设施（不要求一开始就覆盖全站），允许增量迁移现有硬编码字符串。
- 保持代码结构 **locale-ready**（字典/Key 组织稳定），便于社区后续新增翻译而不迫使核心维护者承担多语言复杂度。

**Non-Goals:**

- 不在本变更内完成所有页面/所有文案的全量迁移（允许分阶段）。
- 不内置 `en` 翻译、不做浏览器语言自动选择、不提供语言切换入口与持久化（localStorage）。
- 不引入复杂的翻译平台/外部 SaaS 作为硬依赖（可在后续引入）。
- 不改变后端 API 文案/错误码体系（仅 UI 文案治理与 i18n 占位）。

## Decisions

1. **语言集合与默认策略：仅 `zh-CN`**
   - 核心发行版仅内置 `zh-CN` 文案（默认固定为 `zh-CN`）。
   - 不提供语言切换入口与偏好持久化；未来如需多语言，由社区以增量方式补齐。

2. **最小 i18n 实现：轻量字典 + `t()`（locale-ready）**
   - 增加集中式消息字典（按域分组：workspace/sources/chat/studio/common）。
   - 提供 `t(key, params?)`（以及可选 hook）以避免在组件内散落字符串。
   - Key 采用稳定、可搜索的命名（例如 `workspace.onboarding.no_sources.title`），并保持字典结构可扩展到多 locale，但本次仅提供 `zh-CN`。

3. **增量迁移策略**
   - Phase 1：迁移 Workspace 核心路径的“高频与阻塞”文案（空态/错误/诊断/上传提示），并清理用户可见的英文泄漏点。
   - 后续：逐步迁移剩余面板与边缘弹层文案；多语言翻译由社区增量补齐。
   - 迁移期间允许少量遗留硬编码，但必须逐步减少，避免新增关键路径硬编码字符串。

4. **入口与可发现性**
   - 本次不提供语言切换入口；仅保证核心路径文案集中管理并可扩展。

## Risks / Trade-offs

- **[风险] 翻译质量与术语一致性** → **缓解**：建立简短术语表（Sources/Session/Notebook 等）并在字典中复用；先覆盖核心路径再扩展。
- **[风险] 迁移过程中出现中英文混杂** → **缓解**：以“关键路径全覆盖”为第一里程碑；禁止在关键路径继续新增硬编码中文字符串。
- **[风险] 引入 i18n 依赖导致体积/复杂度上升** → **缓解**：先用轻量字典实现；若未来需要复数规则/日期本地化再引入成熟库。
