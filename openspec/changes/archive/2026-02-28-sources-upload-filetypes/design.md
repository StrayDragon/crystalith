## Context

- 目前 Sources 面板在前端层面把上传文件类型限制为 `.txt/.md/.markdown`，并在拖拽/选择文件时主动过滤掉其他类型；同时 `WorkspaceLayout` 还存在一个隐藏 file input（用于全局上传入口）也使用相同的 `accept` 限制。
- 但后端内置 parser 已支持 PDF（`application/pdf`），且 SDK 文档示例也以 PDF 上传作为常见路径。结果是“后端能处理、文档鼓励、前端却拦截”，形成体验断裂。

## Goals / Non-Goals

**Goals:**

- 在 Workspace 的所有上传入口（Sources 面板上传按钮、全局隐藏 input）中统一支持 PDF 上传。
- 保持前端预过滤与 `accept` 一致，避免“能选但被 toast 拒绝”或“不能选但拖拽能传”的不一致。
- 更新提示文案与单测，使“支持的文件类型”与实际一致，并保留对明确不支持类型的清晰反馈。

**Non-Goals:**

- 不新增后端解析器、不扩大到 docx/pptx 等复杂格式支持。
- 不引入新的后端“supported upload types”端点（可作为后续改进以彻底消除前后端漂移）。
- 不改动 URL 导入/搜索导入等 ingest 路径。

## Decisions

1. **最小支持集先对齐：加入 PDF**
   - 将前端支持集扩展到 `.pdf` / `application/pdf`，作为最常见的 RAG 来源格式之一。
   - 保持 `.txt/.md/.markdown` 现有行为不变。

2. **前端过滤仅作 UX 优化，后端仍为真源**
   - 前端过滤用于快速提示用户“这个文件不会被接受”，减少无效上传。
   - 最终可用性仍由后端 parser 决定：即便前端放行，后端仍可能 415（无匹配 parser）或 400（确定性输入错误）。

3. **统一常量以避免多处漂移**
   - 将上传支持类型（扩展名/MIME/accept 字符串）集中到 Workspace shared 层（如 `shared/uploadTypes`），由 Sources 面板与全局 input 共同引用，避免未来再次发生“入口 A 支持、入口 B 不支持”的问题。

4. **测试覆盖以防回归**
   - 更新前端测试：PDF 必须被视为支持类型；至少保留一个不支持类型（如 `.docx`）用于验证过滤与提示仍有效。

## Risks / Trade-offs

- **[风险] 用户上传更大文件导致处理耗时更长** → **缓解**：上传队列与失败诊断已存在；本变更不改变后端处理策略，仅移除不必要的前端拦截。
- **[风险] 仍存在前后端支持集漂移的可能**（例如未来新增/移除 parser）→ **缓解**：通过“统一常量”降低漂移概率；后续可考虑由后端暴露可用 parser 列表并驱动前端 accept。
