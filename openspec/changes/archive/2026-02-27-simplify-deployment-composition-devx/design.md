## Context

当前项目在本地与部署路径中混合了核心服务和增强依赖的启动假设，导致以下问题：
- 用户不清楚“最小可运行”到底需要哪些服务。
- 可选能力（如向量库、离线模型、检索引擎）对核心链路产生了隐式强耦合。
- 本地与部署入口语义不一致，排障成本高。

我们需要建立一套统一模型：`frontend + backend` 为核心，其他均为可选子服务，通过 Docker Compose 原生能力进行组合。

## Goals / Non-Goals

**Goals:**
- 明确定义核心服务与可选子服务边界。
- 统一本地开发和部署语义（同一组合模型）。
- 使用 Docker Compose 原生机制实现组合，避免引入额外抽象层。
- 为可选服务提供标准化探活、错误语义和降级策略。
- 提供可观测组合状态用于验收与排障。

**Non-Goals:**
- 不在本次变更中替换所有现有外部依赖实现细节。
- 不重写业务 API 协议或前端核心交互模型。
- 不在当前阶段引入 K8s/Helm 或自定义部署 DSL。
- 不在当前阶段将组合清单生成器作为主入口。

## Decisions

### 1) 采用“核心 + profile 可选服务”运行模型
- 决策：将 `frontend`、`backend` 作为唯一核心服务；任何其它服务通过 profile 明确启用。
- 实施映射：在 Compose 清单中分别对应服务名 `web`（frontend）与 `api`（backend）。
- 原因：确保用户可从最小形态稳定启动，再按需叠加能力。
- 备选方案：继续维持“默认全开”。
  - 放弃原因：依赖失败面过大，且不利于用户自托管替换。

### 2) Compose 原生优先：`-f` merge + optional overlays
- 决策：以 Compose 原生合并能力作为主路径（core + optional overlays）；`profiles` 仅作为兼容增强选项，`include` 仅用于强隔离、无命名冲突的模块。
- 原因：用户命令直觉强、文档与工具链成熟、维护成本低。
- 备选方案：Jinja2/Jsonnet/CUE 先行。
  - 放弃原因：引入额外学习与调试成本，当前规模下收益不足。

### 3) 分层清单结构标准化
- 决策：采用“核心基线 + 可选增强 + 环境覆盖”的文件分层；可选服务文件仅写差异，不复制整段核心配置。
- 原因：降低重复和漂移，保障变更可审查。
- 备选方案：单一超大 compose 文件。
  - 放弃原因：可读性和变更边界差，冲突率高。

### 4) 重复片段通过 Compose 原生共享机制收敛
- 决策：使用 `x-` 扩展字段与 YAML anchors 提取公共配置（healthcheck、logging、resources、通用 env）。
- 原因：减少复制粘贴，同时保持 YAML 可读。
- 备选方案：完全手工复制。
  - 放弃原因：长期维护易漂移。

### 5) 探活与自动发现解耦于启动时序
- 决策：可选服务采用周期探活；当服务“后启动”时可自动恢复可用状态。
- 原因：贴合真实开发习惯（先起应用，再起外部服务）。
- 备选方案：仅启动时探测一次。
  - 放弃原因：会造成“必须重启应用才能恢复”的坏体验。

### 6) 组合状态可观测
- 决策：输出核心服务状态、可选服务状态、最后探活时间，并用于部署验收。
- 原因：把“为什么不可用”从隐式失败转换为可诊断信息。
- 备选方案：仅保留日志。
  - 放弃原因：日志不利于自动化验收与快速定位。

### 7) 设立“生成器引入阈值”，但不先做
- 决策：仅当组合复杂度超过阈值（例如可选服务显著增加、文件层次过深、人工合并审查成本过高）时，再评估 `uv + Python` 轻量生成器。
- 原因：先保留最低惊讶路径，避免过早工程化。
- 备选方案：立即引入生成器。
  - 放弃原因：当前阶段会增加认知与维护负担。

## Risks / Trade-offs

- [风险] profile 维度增加后测试矩阵变大
  → 缓解：定义最小矩阵（core-only、core+single-optional、core+all-optional）并纳入 CI smoke。

- [风险] 旧脚本/文档与新语义不一致导致迁移期混乱
  → 缓解：提供兼容别名与迁移映射表，分阶段废弃旧入口。

- [风险] `include` 与 `merge` 混用不当引发命名冲突与不可预期覆盖
  → 缓解：文档中明确“merge-first”规则与 `include` 使用边界。

- [风险] 过度去重导致 YAML 难读
  → 缓解：限制共享片段粒度，优先可读性，少量重复可接受。

## Migration Plan

1. 固化组合约束：定义核心服务、可选 profile、环境覆盖与命名规范。
2. 重构清单结构：按分层规则整理 `deployments/`，并补齐共享片段。
3. 改造启动入口：Procfile/开发入口对齐核心+profile语义，保留兼容映射。
4. 接入探活状态聚合：保证可选服务后启动可恢复、核心链路不受阻塞。
5. 更新文档与验收清单：补齐最小启动、增强启动、自托管替换路径。
6. 评审后进入实现：本变更文档完成后再进入代码与部署清单改造。

回滚策略：
- 保留旧入口兼容开关；若新组合模型异常，可暂时回退到旧入口并禁用新 profile 解析。

## Open Questions

- 是否需要单独的 `/health/dependencies` 端点，还是扩展现有 `/health` 即可？
- 可选服务失败时，前端提示是否区分“可重试（等待服务启动）”与“配置错误（需人工修复）”？
- CI 是否需要引入 profile 级别并行 smoke job，还是先从 nightly 开始？
- `include` 策略结论：默认禁用；仅在“无同名冲突且强隔离”的独立模块中按评审单独放开。
